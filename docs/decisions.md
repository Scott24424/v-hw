# 결정 기록

- [2026-07-29] .claude/settings.json의 deny 규칙을 `Read(./.env)` → `Read(.env)` (및 `.env.*` 동일)로 수정. 공식 문서(code.claude.com/docs/en/permissions) 기준 지원되는 앵커 형식은 bare filename / `/path` / `//path` / `~/path` 뿐이며 `./path`는 명시되어 있지 않아 매칭이 보장되지 않음. bare filename 형식은 `**/.env`와 동일하게 어떤 깊이에서도 매칭됨이 문서로 확인됨.
- [2026-07-29] `Assignment.date`를 `DateTime`이 아니라 `String`("YYYY-MM-DD")으로 저장. SQLite에 DATE 타입이 없어 Prisma `DateTime`은 타임스탬프로 저장되고, KST(+9)에서 자정 경계마다 하루 밀리는 버그가 구조적으로 발생함. ISO 문자열은 사전순=시간순이라 범위 쿼리·인덱스가 그대로 동작. 대가로 날짜 유틸을 직접 만들고 단위 테스트로 덮는다.
- [2026-07-29] 시각은 `Int`(자정 기준 분)로 저장. 실물 시간표가 12시간제 표기라 "2:00"의 오전/오후가 모호한데 정수 정규화로 저장 시점에 해소되고, 정렬·겹침 검사가 산술 비교로 끝남.
- [2026-07-29] 과제 유형은 단일 `Assignment` 테이블 + `type` enum으로 모델링(유형별 분리 테이블 기각). 핵심 기능이 "유형 무관 남은 것 전부를 날짜순"이라 단일 인덱스 스캔으로 끝나야 하는데, 분리 테이블은 Prisma에 다형 관계가 없어 매번 N회 쿼리 후 앱 메모리에서 병합·재정렬해야 함. 대가인 nullable 컬럼 4개는 앱 레벨 검증으로 커버. 읽기 전용 필드가 6개를 넘으면 `ReadingDetail` 1:1 분리로 이전.
- [2026-07-29] "밀림(overdue)"은 상태로 저장하지 않고 `date < 오늘 && status ∈ {PLANNED, IN_PROGRESS}`로 계산. 저장 방식은 자정 배치가 필요한데 상시 구동 PC가 절전에 들어가면 DB가 거짓말을 하게 됨. 단 "오늘"의 기준은 서버(Asia/Seoul) 한 곳으로 두고 API가 `isOverdue` 파생 필드를 내려보냄 — 기기별 시계가 어긋나 아이패드와 폰이 다른 목록을 보여주는 것을 막기 위함.
- [2026-07-29] 시간표는 `RoutineBlock` 템플릿만 두고 날짜별 행을 실체화하지 않음. "시간 틀은 매일 동일, 내용만 다름"이라는 요구사항과 정확히 일치하고 생성 배치가 불필요. "오늘만 시간 변경/건너뛰기"가 필요해지면 `ScheduleInstance` 테이블 추가 + 행 없으면 템플릿 폴백으로, 기존 데이터 변경 없이 이전 가능.
- [2026-07-29] docs/architecture 브랜치를 main이 아니라 chore/agent-rules HEAD 기준으로 생성. main에는 `.gitignore`/`README.md`뿐이고 CLAUDE.md·decisions.md·worklog.md가 전부 미머지 상태의 chore/agent-rules에만 있어, main 기준으로 파면 두 문서를 새로 만들게 되어 충돌이 확정됨. PR base도 chore/agent-rules로 둔다.
- [2026-07-29] architecture.md §7.1 의존성 4건(vitest, zod, Tailwind CSS, create-next-app 스캐폴딩) 전부 사용자 승인. 테스트 러너는 vitest, E2E는 Playwright 추가 확정 — 사용자가 명시적으로 지정.
- [2026-07-29] 백업은 1차 버전에서 SQLite 파일 직접 사용(§0.3의 "집 PC 단독 소유" 전제 유지) + `npm run backup` 스크립트로 `prisma/dev.db`를 `backups/`에 타임스탬프 붙여 복사. 원격 복제나 자동 스케줄링은 하지 않음 — 사용자가 1차 범위를 수동 스크립트로 한정. `backups/`는 `.gitignore`에 추가(DB 스냅샷은 커밋 대상이 아님).
- [2026-07-29] 취침 시각·주말 구분을 architecture.md §7.2대로 미해결로 남기지 않고 "실물대로 간다"로 확정: 시간표는 17:00 종료, 요일 구분 없음(주말도 평일과 동일 템플릿 적용). 근거: 실물(daily-schedule.jpg)에 취침 블록과 요일 구분이 애초에 없고, 사용자가 실물을 있는 그대로 옮기는 것을 이번 범위로 확정. 취침 블록이나 주말 전용 템플릿이 필요해지면 RoutineBlock에 dayOfWeek? 필드를 추가하는 방식으로 이전 가능(기존 데이터 변경 없음).
- [2026-07-29] `prisma/schema.prisma`의 `datasource url`을 `env("DATABASE_URL")` 대신 `"file:./dev.db"` 리터럴로 고정. CLAUDE.md가 .env 파일 읽기·수정·더미값 삽입을 금지하고 있어 env() 참조 시 필요한 `.env`를 만들 수 없음(prisma generate/validate가 env var 부재 시 에러). 이 값은 비밀이 아니라 "집 PC가 SQLite 파일 하나를 단독 소유"라는 이미 확정된 배포 결정 그 자체이고, 배포 환경이 하나뿐이라 환경별로 달라질 이유가 없어 리터럴로 고정해도 손실이 없음. 여러 환경을 지원해야 하는 시점이 오면 그때 env() 참조로 전환.
- [2026-07-29] Prisma 스키마는 이번 스캐폴딩 단계에서 모델 없이 datasource/generator만 정의(빈 상태). 모델은 architecture.md §1을 근거로 후속 커밋에서 기능 단위로 추가 — 스캐폴딩 커밋과 스키마 커밋을 섞지 않는다(CLAUDE.md "기능 단위로 작게 커밋").
- [2026-07-29] vitest 기본 environment를 `jsdom`이 아닌 `node`로 설정. 이번 스캐폴딩에는 React 컴포넌트 단위 테스트 대상이 없고(날짜/진도 계산 같은 순수 로직 테스트가 우선), jsdom + 관련 패키지는 실제로 컴포넌트를 테스트하기 시작하는 시점에 추가.
- [2026-07-29] `vitest.config.ts`에 `resolve.alias`로 `@` → 프로젝트 루트를 수동 등록. `tsconfig.json`의 `paths`는 tsc/Next 빌드에만 적용되고 vitest(Vite)는 이를 자동으로 읽지 않아, alias 없이 `@/lib/...` import가 테스트에서만 실패함(`vitest.config.ts` 신설 이후 재발 가능한 함정이라 기록).
- [2026-07-29] 과제 생성 검증은 zod `superRefine`으로 architecture.md §2.2의 유형별 필드 규칙(READING만 bookId/progressUnit/progressEnd 필수, 그 외는 전부 null)을 강제. `progressStart` 자동 채움(직전 과제의 progressEnd+1)은 스키마가 아니라 라우트 핸들러에서 처리 — DB 조회가 필요해 순수 검증 로직인 zod 스키마의 책임 범위를 벗어남.
- [2026-07-29] `/api/assignments` 라우트 핸들러 자체(DB 연동)에 대한 단위 테스트는 만들지 않고, 이미 구성된 Playwright(`e2e/`)로 실제 dev 서버 + SQLite에 대고 검증. 이유: Next App Router route handler를 순수 함수로 목(mock) 테스트하려면 Request/Response 목킹 인프라를 새로 만들어야 하는데, Playwright는 이미 webServer 기동을 자동 처리하고 있어 실제 환경에 더 가깝게 검증 가능. zod 스키마·날짜 유틸 같은 순수 로직만 vitest 단위 테스트로 커버.
- [2026-07-29] `e2e/assignments-api.spec.ts`에 `test.describe.configure({ mode: "serial" })` 추가. Playwright의 `beforeAll`은 파일을 실행하는 워커마다 한 번씩 실행되는데, 기본 병렬 워커 설정에서 같은 제목의 Book을 동시에 생성하려다 unique 제약 충돌 발생(실제로 재현·확인함). DB 상태를 공유하는 e2e 스펙 파일은 앞으로도 serial 모드를 기본으로 고려할 것.
